# SwiftUI compatibility assumptions

ScopedAnimation depends on how SwiftUI passes transactions through view
modifiers and hosted content. These are observed behaviors rather than an Apple
guarantee that every framework version will propagate transactions identically.

The [design](../HANDOFF.md) defines the library contract. This document identifies
the assumptions that make it possible, their executable checks, and the limits
of available evidence.

## Compatibility gates

| Assumption | Required behavior | Automated coverage |
| --- | --- | --- |
| Boundary stripping | Setting transaction animation to nil removes both explicit and ancestor implicit animation before it reaches content. | `AnimationBarriersTests.swift`, `AnimationProxiesTests.swift` |
| Local restoration | A descendant transaction hook can set animation after an ancestor hook strips it. | `AnimationAssumptionsTests.swift` |
| Explicit stamp propagation | A custom transaction key supplied through `withTransaction` reaches root and descendant observers. | `AnimationProxiesTests.swift` |
| Local value stamping | A resolver can supply animation and a scope stamp to descendants without sending either upward. | `AnimationValuesTests.swift` |
| Value gating | `.transaction(value:)` applies its transform for tracked changes and does not animate unrelated updates. | `AnimationAssumptionsTests.swift`, `AnimationUpdateSequenceTests.swift` |
| Nested ownership | Boundaries preserve a nonmatching stamp while removing animation; a matching descendant can restore it. | `AnimationProxiesTests.swift`, `AnimationBarriersTests.swift` |
| Diagnostic placement | A root observer sees explicit animated transactions, but cannot see animation generated by a value modifier below it. | `AnimationDiagnosticCoverageTests.swift` |
| Stable content identity | Changing trigger count preserves scoped content state while establishing a new value baseline. | `AnimationTriggersTests.swift`, `AnimationUpdateSequenceTests.swift` |

Test paths are relative to `Tests/ScopedAnimationTests/`. Tests run inside a
serialized main-actor suite and retain their SwiftUI hosts. The transaction spy
requires an observation before accepting an absence-of-animation assertion.

If boundary stripping, local restoration, or stamp propagation fails on a target
runtime, dependent implementation work stops for a reproduction and design
review. Do not redefine the public semantics to conceal a framework incompatibility.

## Observation direction

```text
withTransaction(animation + stamp)
    ├─ root observer can see the stamp
    └─ descendant observer can see the stamp

root observer
    └─ local value animation + stamp
        └─ descendant observer can see the stamp
```

This distinction explains why a root detector cannot find every raw
`.animation(_:value:)` source. Install a detector downstream of the suspected
source or use a barrier at the region that must reject its animation.

## Foundation probe evidence

Recorded environment: **2026-07-03**, Xcode 26.5 (17F42), Apple Swift 6.3.2,
iPhone 17 Simulator, iOS 26.5. A standalone `SwiftAnimationSpike` package exercised
raw SwiftUI hooks. That exploratory package is not distributed in this repository;
the maintained checks are the library test files listed above.

The observations establish:

- Stripping removed animation while control views received it.
- Local value changes supplied animation inside a boundary.
- Explicit stamps reached root and child; local value stamps reached only child.
- Five updates through 60 observed rows produced 300 row callbacks. The elapsed
  time includes run-loop pumping and is not a CPU benchmark.
- The List container and lazy rows were observed, but List row callbacks were
  absent. Zero callbacks cannot establish row-level blocking or reuse behavior.
- The tracked overlay frame changed with scrolling and host resizing.

## What hosting does not establish

Transaction tests verify the animation and stamp supplied to content. They do not
measure interpolation, rendered frames, or frame rate. Transition and
matched-geometry transaction delivery therefore need visual checks for
application-specific behavior.

The sample app's [QA procedure](../Examples/QA.md) covers List row propagation,
barriers, reuse, visible outlines, and interactive composition. Its recorded
results apply only to the stated environment. A successful sample build does not
replace those checks.

Use [CONTRIBUTING.md](../CONTRIBUTING.md) to rerun automated checks.
[Validation results](validation.md) record the tested environments and outputs.
